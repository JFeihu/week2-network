# Day 2 · asyncio：为什么单线程也能"同时"干 10 件事

> 今天以阅读和观察为主。实验代码已写好（`slow_server.py` + `bench.py`），
> 你可以随时自己跑一遍：先 `uv run python slow_server.py`，另开终端 `uv run python bench.py`。

## 实验数据（跑出来就是这样）

10 次请求，每次服务端延迟 0.3 秒：

| 方式 | 耗时 | 相对同步 |
| :-- | --- | --- |
| 同步（一个接一个） | 3.37 s | 1× |
| 线程池（10 线程） | 0.48 s | 7× 快 |
| 异步（`asyncio.gather`） | 0.57 s | 6× 快 |
| 异步但内部用 `time.sleep` | 3.00 s | 没变快 |

---

## 1. 协程、线程、进程，三者的区别？

（提示：从"谁在切换"和"适合什么任务"两个角度写）

- 进程：由操作系统内核切换，开销大；适合 CPU 密集任务，可多核并行。
- 线程：由操作系统内核切换，开销中等；适合 IO 密集任务，Python 受 GIL 限制不能并行计算。
- 协程：由用户程序主动切换，开销很小；适合高并发 IO 密集场景，如异步网络请求。
- **线程的栈约 1MB，协程只有几 KB**——所以“1 万个并发”，线程撑不住，协程很轻松。

## 2. 同步为什么是 3.37 秒，而异步只要 0.57 秒？

（提示：同步在等的时候，CPU 在干什么？异步在等的时候，它在干什么？）

同步时遇上程序阻塞，CPU只能等到阻塞关闭后再继续运行，期间就只能等待，而异步时，await会交出CPU的控制权，这样就能在事件循环中跳过程序阻塞，进行下一步操作，等到阻塞完成后再回来继续完成作业。

## 3. `await` 到底做了什么？

（提示：不是"等待"，而是"把控制权交出去"。交出去之后谁接管了？）

await = 把控制权交会事件循环，事件循环从“就绪队列”里挑下一个协程继续跑。被 await 的对象完成后，事件循环再把控制权还回来，从 await 的下一行继续

## 4. 为什么在 `async def` 里写 `time.sleep(0.3)` 会让程序退回 3 秒？

（提示：`time.sleep` 阻塞的是谁？那个"谁"被卡住之后，其他协程还能跑吗）

如果非要调同步库（比如 `requests`），应该怎么写？

`time.sleep` 阻塞的时当前线程。而事件循环就跑在这个线程上——当前事件循环一睡，整个循环就停摆，其他9个协程谁也得不到调度。于是并发退化成穿行

应该用异步版 sleep  ==  ==await asyncio.sleep(0.3)==



## 5. `gather` 和 `TaskGroup` 的区别？

（提示：其中一个任务抛异常时，另一个任务会怎样？）

gather：默认情况下，一个任务抛出异常，第一个异常立即向上传播 **不会取消其他正在运行的任务**，其余任务继续执行；

TaskGroup：任意一个任务抛出异常，**会立刻取消组内其他所有正在运行的任务**，然后等待被取消的任务收尾，再抛出异常。

## 6. 什么情况下异步"没用"？

（提示：CPU 密集的任务，比如算质数、图片压缩——为什么异步帮不上忙）

当程序执行CPU密集的任务时，既这一任务离不开CPU运算时，异步是没有用的，因为await一旦交出CPU控制权，当前程序运行也会随之停止，后面切换回来也要继续未完的运算。

## 7. 一句话总结

用你自己的话说：**asyncio 到底在解决什么问题？**

解决程序同步阻塞问题，增加CPU的使用效率，在程序阻塞并且CPU不在密集任务中时，这一点体现的尤为明显。

asyncio 让一个线程在“等IO”的时间里去做别的事情，从而提高单位时间内完成的请求数，不是提高CPU算力
